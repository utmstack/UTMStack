# UTMStack ingest / EventProcessor perf notes

## Where the "event processor" actually lives (2026-11-05)
- The ingestion engine is **NOT in the UTMStack monorepo.** It is the separate repo **`D:\Projects\github.com\utmstack\EventProcessor`** (module `github.com/threatwinds/EventProcessor`), built into the `eventprocessor` binary + **15 separate `.plugin` OS processes** that talk to each other over **gRPC on unix sockets** (`/workdir/sockets/<name>_<stage>.sock`). go-sdk v1.1.38 (module cache `C:\Users\osmon\go\pkg\mod\github.com\threatwinds\go-sdk@v1.1.38`).
- `event_processor.Dockerfile` (in the monorepo) only COPYs the compiled plugins; the `eventprocessor` base image comes from `ghcr.io/utmstack/eventprocessor/base`.
- Stages: parsing → analysis → correlation → notifications. Parsing ops (json/rename/grok/add/delete/cast/trim/csv/xml/kv/reformat) and analysis (cel/feeds/sew) are each their own process. **Every pipeline step marshals the ENTIRE document** (the `Draft.Log` string) across the process boundary, and the engine runs an in-process CEL `where`-guard (`evalWhere`) per guarded step too.

## Measured per-event CPU (real AWS events through the live engine, 2026-11-05)
- **~28.5 ms CPU per AWS event**, decomposed: **cel.plugin ~12ms (43%)**, engine ~9ms (31%), rename ~2.7ms, grok ~2.2ms, json ~1.1ms, add ~0.7ms. Confirms the "eventprocessor + cel + rename eat CPU" report.
- Why: the **cel plugin runs 81 rules for `aws`** (43 google, 71 o365, 40 azure) and `cel.go:184-192 Eval()` **re-serializes the full event to protojson + unmarshals to a map on EVERY rule** — that's 81 full-event (de)serializations/event. Engine also does ~85 in-process CEL where-evals + 128 gRPC full-doc crossings (AWS filter has **128 steps**).

## Recent regression (the dependency-update work)
- Commit **`0a6303a228` (2026-10-12, "feat(utm-bag)")** in the **UTMStack** repo bumped all modules to go-sdk v1.1.38 AND added the `utm.*` aggregatable bag: **AWS filter 96→128 steps, O365 56→80** (all new `grok` copy-steps with `exists()` CEL guards). Lands ~2 weeks before the heavy Oct 28–30 ingest burst. This raised per-event cost ~30% right before peak volume.

## Structural latency floor (independent of CPU)
- `plugins/events/queue.go`: OpenSearch **`NewBulkQueue(FlushInterval: 10s, FlushThreshold: 50)`** → sub-50 batches wait **up to 10s** to be indexed. This is the guaranteed ingest-latency floor on low-volume streams (e.g. O365 ~27/day), plus O365's own ~5-min Graph polling window.

## snakeyaml is NOT bumpable to 2.x on the current Spring Boot (2026-11-11)
- Spring Boot 3.1.5 (backend) + 2.7.14 (user-auditor, web-pdf) rely on spring-core `OriginTrackedYamlLoader`, which calls the **no-arg `org.yaml.snakeyaml.representer.Representer()` ctor that snakeyaml 2.0 REMOVED** ΓåÆ `NoSuchMethodError` at startup. ## Box API access facts (for e2e, 2026-11-12)
- UI is HTTPS-only via host nginx (`:80` -> `:443`); the in-app browser rejects the self-signed cert (and I won't bypass cert checks), so UI e2e = drive the **real API surface the Angular app calls** through the frontend container: `docker exec <frontend> curl http://localhost/api/...` (the container nginx listens on **:80**, not 443 — using 443 gives HTTP 000/no connection).
- **Every `/api` call needs the `X-Shared-Key` header** = value of `set $shared_key ...` in the frontend's `/etc/nginx/conf.d/00_nginx_panel.conf` (host-internal frontend<->backend guard key, also embedded in the public JS bundle). Without it -> 403.
- **Login** = `POST /api/authenticate` with `{"username","password","rememberMe":false}` — `rememberMe` is REQUIRED (null Boolean -> `NPE: LoginVM.isRememberMe() is null` -> HTTP 500). MFA is on by default; to bypass for testing: `docker service update --force --env-add APP_TFA_ENABLED=false utmstack_backend` (backend `TokenProvider.shouldBypassTfa` reads this env), then login returns a full token directly. **ALWAYS `docker service update --env-rm APP_TFA_ENABLED utmstack_backend` after** (I left it set twice and had to restore). The admin app password is NOT the box OS password.
- **`/api/elasticsearch/search`** (UI log/alert list) takes **`?top=&indexPattern=` query params + a JSON array of FilterType as the body** (e.g. `[]`) — NOT a `{indexPattern,page,size}` JSON object (that shape 500s; that was my own test bug). Overview endpoints (`top-alerts`, `count-alerts-by-*`, `events-in-time`, `top-windows-events`) all require `from`/`to` (and `top`) query params; calling them bare 500s (also my own test bug — the UI always sends a time range).
- **Re-cut deploy gotcha:** the installer updater tracks by version string (`v11.4.0`), so re-cutting the SAME tag (new image digests) does NOT make it re-pull — the box keeps the old image. To force it: `docker service update --force --image ghcr.io/utmstack/utmstack/backend:v11.4.0 utmstack_backend` (only re-pull the services whose image actually changed; for 35fc692->221be9d only the backend changed).

## Local Docker frontend build recipe (2026-11-12)
- This box has Docker (29.9.2) + a `node:18.20` image — so I CAN build/verify the Angular 17 frontend locally (unlike my earlier snakeyaml/sqlcheck re-cuts where I only had `mvn package` + the box). Recipe: stage `frontend/` to a Windows path, `docker run --rm -v <win>:/w -w /w/frontend -e NODE_OPTIONS=--max_old_space_size=8192 node:18.20 bash -c "npm install --no-audit --no-fund && npx ng build --configuration production --base-href /"`. **Gotcha: under `bash` (MSYS2) `/w` mangles to `W:/`** — run the docker command from PowerShell (or use `cmd //c`) and pass the mount as `C:\...\dir:/w`. `npm ci` from the committed lock = exactly what CI does; regenerate the lock with npm 10.8.2 to keep lockfileVersion 2.
