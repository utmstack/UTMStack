## Historical overview and measurements

This workspace contains an **experimental in-process Go replacement for the ClamAV daemon path**. The EDR loads local or signed remote signatures, scans files and AMSI buffers, recurses into many containers, and passes detections to the existing response pipeline. The ClamAV process, scan socket and `freshclam` updater are gone from this path. It is **not yet a feature-equivalent replacement** and must not be represented as production-equivalent protection. The engine reports `partial-signature-and-format-support` deliberately.

**The complete official feed now loads** (main 63, daily 28133, bytecode 339): `sigaudit` reports 0 rejected rules; all 3,628,578 rules the reference loads at functionality level 216 are accepted. Rules whose analysis this engine does not perform yet load as **"unknown when reached"** (rick's decision of 2026-09-24): such a rule makes an object's result incomplete only where it could apply, never clean and never a detection. On daily 28134 (2026-09-26), 1,448 rules are in that state: 1,185 regular-expression rules, 109 image-hash rules, 80 icon-group rules (groups no icon entry carries are decided false), 30 certificate-trust rules, 12 bytecode programs (21 before the bytecode runtime work of 2026-09-25/26), 11 handler-type rules, 10 phishing allow rules, 10 version-information rules (decided on every PE header this engine models) and 1 byte-comparison rule. Normalized HTML is produced since 2026-10-03 and macro projects since 2026-10-08 (below).

Measured on cloud VMs against ClamAV 1.4.3 with the same database (details below): **no clean result where the reference detects**, on the 44 upstream test files and on 836 wrapped copies; **no false positive** on 78,583 Debian files or 68,460 Windows System32 and Program Files files; about 3.5 times faster than the reference with one worker. Still open: 15 test files and their wrapped copies are incomplete (packers, 7z, CHM, Deflate64, implode, AutoIt, InstallShield), 2.8% of Linux files and 4.4% of Windows files come back incomplete, and memory is about 2.5 GB for the Windows service. ## What changed on 2026-10-14 (native-go-v18): compound files read as the reference reads them

## What changed on 2026-09-27: image fuzzy hashes

The 109 official `fuzzy_img#` rules made every PNG, GIF and JPEG incomplete. `signatures/imagehash.go` now computes the reference's image hash (grey value `round((299R + 587G + 114B) / 1000)` ignoring alpha, a transparent pixel keeping its color; Lanczos3 resize to 32x32, vertical pass first, rounded; the 8x8 lowest frequencies of the cosine transform against the average of their two middle values; bits in row order) with Go's PNG, GIF and JPEG decoders. The reference's documentation only says the hash is close to the common pHash; the details were learned from its own hashes (its signature tool's image-hash command) of 4,446 Windows Server images and 700 generated ones: 4,022 of the 4,078 decodable images get exactly the reference's hash.

Where this engine cannot be sure of a bit it says so: a resized pixel within 0.01 of a rounding boundary may round the other way in the reference's single-precision arithmetic, and a JPEG pixel may differ by 1 between decoders; each such pixel bounds how far every coefficient and the median can move, and a bit that close to the median (or tied with it) is uncertain. An image flat after resizing has a certain hash (`8000000000000000`, or 0 for black; 1,627 of the Windows images). A rule is false when a certain bit differs from its hash, a detection only when every bit is certain and equal, and unknown otherwise; BMP, TIFF, ICO and other formats stay unknown. No certain bit differs from the reference on any of the 4,078 images (`TestImageHashAgreesWithReference`, with 369 generated images checked in and `EDR_IMAGE_ORACLE` for the larger set). Two speed fixes came from the measurement: the resize reads rows, not columns, and common pixel layouts are read directly (an archive of 6,000 images went from about 98 s to 58 s).

The relevant data flow is:

```text
watcher / manual scan / AMSI
    -> scanner or AMSI adapter
    -> Engine.ScanSnapshot (one immutable signature generation)
    -> raw signatures and bounded recursive format handling
    -> detected / clean / incomplete verdict
    -> generation-aware cache, event, quarantine or AMSI policy

approved feed inputs -> feedpack -> signed manifest + artifacts
    -> HTTPS updater -> verify -> compile every rule -> durable generation
    -> atomic activation -> clean-cache identity changes
```

An incomplete result is an **unknown analysis outcome**, not a malware detection and not a clean result. It is never cached as clean. It does not by itself trigger malware quarantine. AMSI's existing fail-open/fail-closed setting governs what happens to an incomplete script scan.

### Format work and evidence

- **CAB:** `engine/cab.go` supports complete single-cabinet stored and MSZIP folders, including 32 KiB MSZIP history across blocks, reserved fields, optional XOR block checksums, bounds and expansion limits. `cab_test.go` covers multi-block history, nested gzip, PE overlays, malformed offsets/checksums and unsupported variants. Quantum, LZX and multi-cabinet sets remain incomplete. The implementation was informed by [Microsoft MS-CAB](https://download.microsoft.com/download/4/D/A/4DA14F27-B4EF-4170-A6E6-5B1EF85B1BAA/%5BMS-CAB%5D.pdf), [MS-MCI](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-mci/3048c471-f739-4d30-bcb3-a962cfe84a69), and [ClamAV's libmspack integration](https://github.com/Cisco-Talos/clamav/blob/main/libclamav/libmspack.c).
- **TNEF and compressed RTF:** `engine/tnef.go` scans legacy attachment data, selected encapsulated MAPI properties, Unicode text, recipients and embedded objects. Attribute checksums are verified. `engine/rtfcomp.go` handles both MELA and LZFu RTF compression with CRC, 4096-byte history and output limits. `tnef_test.go` checks Microsoft's published LZFu example/CRC and synthetic nested attachments. Unknown property types and embedded objects without a supported interpretation stay incomplete. References: [MS-OXTNEF](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxtnef/b03b5704-ef54-4390-b981-dc78f8e79a05), [MS-OXRTFCP](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxrtfcp/65dfe2df-1b69-43fc-8ebd-21819a7463fb), [ClamAV TNEF source](https://raw.githubusercontent.com/Cisco-Talos/clamav/main/libclamav/tnef.c).
- **Uuencode:** `engine/uuencode.go` decodes traditional and `begin-base64` envelopes in generic text and recognized mail bodies, then recursively scans the decoded bytes. `uuencode_test.go` checks the known `Cat` encoding, nested gzip, MIME embedding and malformed envelopes. This follows [POSIX uuencode](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/uuencode.html); nonstandard variants need a real mail corpus.

ClamAV's open-source code was used as a **reference**, not linked into the Go engine. The new code does not require ClamAV at runtime. Before directly copying any upstream code or test assets, review the relevant upstream license and attribution requirements; the upstream TNEF source, for example, carries a GPL notice.
