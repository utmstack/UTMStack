# Bytecode API reference and compatibility profile

The [v241 audit](../../../docs/edr/native-engine/audits/2026-11-07-v241-quantum/REPORT.md)
adds positive extracted-child checks for the authenticated GandCrab CBC
`6539706`, SHA-256
`f93354db8e201d386a1cd05b92ffe37116885fd7da9cd09f27f845754ba10db3`.
All three cipher branches and both key-section locations produce the same
child in Go and ClamAV. Its output, MPRESS, LizardNest, script2exe and
hta2exe cover selected positive paths in all five level-234 activatable
programs declaring `write`. This is declaration/path evidence, not proof
that every execution of those programs is equivalent. The ELF writer
`7086472` declares a 110–119 functionality window and remains excluded.

Positive output validation now includes four authenticated v339 programs:
script2exe, hta2exe, MPRESS and LizardNest. Each generated harmless parent
reaches a child-only hash detection in Go and pinned ClamAV 1.5.4. MPRESS
and LizardNest also check exact child SHA-256 and size in the reference
trace. The [v240 audit](../../../docs/edr/native-engine/audits/2026-11-07-v240-word6-macros/REPORT.md)
pins their inputs and output. This validates selected output paths and
does not establish every official program, format variant or host codec API.

Wire APIs 102–104 use the pinned [ClamAV 1.5.4 LZMA pipe
adapter](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L888-L975)
and [stream interface](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/lzma_iface.c#L60-L131).
The Go VM consumes the 13-byte LZMA-alone header at init, decodes complete
streams within a single input/output window, and returns stream end (`2`).
Bytes after a completed stream remain available in the source pipe. Partial
or uncertain cursor behavior stops incomplete. Four harmless
native/Go cases agree in the [v194 oracle](../../../docs/edr/native-engine/audits/2026-11-01-v194-clambc-lzma/REPORT.md).

Wire APIs 105–107 use the pinned [ClamAV 1.5.4 bzip2 pipe
adapter](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L976-L1061).
The Go VM recognizes their exact declarations and processes complete
streams within a single input/output window using Go's bzip2 decoder.
`bzip2_process` returns `BZ_STREAM_END` (`4`) for that supported case;
the first stream's verified end leaves later bytes in the source pipe.
Partial windows and uncertain cursor/error behavior stop incomplete. The
[v193 oracle](../../../docs/edr/native-engine/audits/2026-11-01-v193-clambc-bzip2/REPORT.md)
checks a decoded child under a bytecode branch that requires status `4`
and zero remaining input against the retained interpreter.
The [v204 differential](../../../docs/edr/native-engine/audits/2026-11-01-v204-bytecode-stream-tail/REPORT.md)
checks bzip2 and LZMA programs that require exactly one trailing byte.

Wire API 91, `get_file_reliability`, returns the scan context's
`corrupted_input` field, or `3` without a scan context in the pinned
[ClamAV 1.5.4 implementation](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1877-L1881).
Go supplies `0` only for a proved normal root representation; a reached
query on an unproved nested/reconstructed representation is incomplete.
The [v192 oracle](../../../docs/edr/native-engine/audits/2026-11-01-v192-file-reliability/REPORT.md)
checks a positive root and three clean native/Go controls.

## Wire identifiers and prototypes

Wire API IDs are **one based**. The generated C table is zero based: the [loader](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L930) decrements the serialized ID and checks its name and complete function prototype. Accepting a familiar name with a mismatched ID or type is incorrect. All functions in this table return type `32`; pointer arguments use predefined type `65`, an 8-bit integer pointer. Signedness is interpreted by the API; it is not a separate wire integer type.

## Host behavior

Maps (wire IDs 57–64) follow [ClamAV 1.5.4's API wrappers](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1292-L1422) and [underlying map storage](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/hashtab.c#L806-L989). `map_new` rejects a zero key size; negative key/value sizes enter an unchecked-initialization path upstream, so Go stops incomplete. `map_addkey` returns 1 for a new key and 0 for a duplicate, retaining that slot as `last_insert`; `map_setvalue` updates it. `map_find` returns 1 on a hit and 0 on a miss, retaining `last_find` on a miss. Removal returns 1 for a present key, zeroes a fixed value or frees a dynamic one, and leaves the last indices unchanged. Fixed `map_getvaluesize` reports its declared size even before a lookup; dynamic maps report the last-found slot size or `-1` before a lookup. `map_getvalue` requires the exact size and returns a writable pointer to the selected slot or null. Fixed values use contiguous storage that is replaced on growth, so stale pointers fault rather than depending on whether C `realloc` moved. Dynamic value replacement and `map_done` retire their pointers. The VM bounds maps to 4,096, accumulated value slots to 262,144, live key bytes to 32 MiB and value storage to its existing 32 MiB virtual-memory cap; hitting a cap is incomplete. [ClamAV's allocator](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/others_common.c#L209-L245) rejects zero-byte `malloc`/`calloc`; accordingly a zero-size dynamic value update returns `-1` after freeing the former value, and `buffer_pipe_new(0)` returns `-1`.

Buffer pipes (wire IDs 30–38) follow the [ClamAV 1.5.4 implementations](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L633-L770). `new(size)` creates zeroed, fixed-capacity storage; `new_fromfile(pos)` starts a read-only pipe at a valid non-EOF file offset. Invalid IDs return zero for availability/get queries and `-1` for stopped/done calls. `read_get` and `write_get` return null for zero or excessive lengths. Memory-backed writes advance only at `write_stopped`; reads advance only at `read_stopped`, which resets both cursors after the entire buffer fills and is consumed. There is no sliding compaction. File-backed `read_avail` is capped at the C runtime's `BUFSIZ` (512 Windows, 1,024 Darwin, 8,192 glibc Linux target profile); `read_stopped` advances its unsigned cursor, and writes are unavailable. The Go VM maps file-backed pointers to one read-only view of its input snapshot, preserving offset identity without a second file copy. `done` retires memory-backed pointers. A later use of the destroyed slot returns `ErrRuntime` because upstream can interpret a freed memory buffer as a file pipe; this avoids a false clean result from undefined lifecycle behavior. Cursor arithmetic overflow on a memory pipe also returns `ErrRuntime` rather than following the source's unsigned-wrap behavior. The VM caps pipes at 4,096 and charges allocations/reads to the work budget. The Windows and Linux C-library window sizes are source-profile assumptions pending native differential validation.

Stateful inflate (wire IDs 39–41) follows [ClamAV 1.5.4's zlib adapter](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L772-L887). `inflate_init(from,to,windowBits)` allocates an ID after checking both pipe IDs; invalid `windowBits` consumes a slot and returns `-1`. `inflate_process(id)` requires both available input and output, advances their cursors by the exact bytes zlib consumes and produces, and returns zlib's integer status (`Z_OK=0`, `Z_STREAM_END=1`, `Z_NEED_DICT=2` or a negative status). End of stream closes the ID. `inflate_done(id)` closes an active ID and returns zero; an invalid or already closed ID returns `-1`. The Go decoder implements raw DEFLATE, zlib, gzip and automatic zlib/gzip wrapper selection, including stored/fixed/dynamic blocks, 32 KiB history, checksums and gzip optional headers. It implements the [zlib Huffman table validity rules](https://github.com/madler/zlib/blob/v1.3.1/inftrees.c#L976-L991) and the [dynamic symbol-count bound](https://github.com/madler/zlib/blob/v1.3.1/inflate.c#L3761-L3785). After a data error, the adapter runs `inflateSync`'s full-flush-marker search across calls, preserving marker progress and zlib's return status; a marker resumes decoding with a reset history and disabled wrapper checksum. Preset-dictionary headers consume the dictionary ID and return `Z_NEED_DICT` with zlib-matched cursors on subsequent calls; the ClamBC host API has no dictionary setter, so it cannot resume decoding that stream. The Go VM bounds inflater slots to 256 per run, with an approximately 32 KiB history buffer each, and charges available input/output against the work budget before processing. A test-only C zlib adapter verifies exact per-call cursors, output and statuses on selected valid and corrupt streams; native ClamBC differential behavior remains unverified on Windows and Linux.

JavaScript normalization (wire IDs 43–45) follows the source's `jsnorm_init/process/done` lifecycle. `init(from)` requires an existing pipe and allocates an ID; `process(id)` consumes all currently available input from that pipe and returns zero, or `-1` for an invalid ID or empty pipe; `done(id)` finalizes one normalizer and queues its `<script>` output for scanning after VM execution. The Go implementation reuses the HTML script tokenizer in `edr/jsnorm`, bounds normalizer count and aggregate bytes, and scans completed output through the enclosing recursive-child callback. A reached output with no callback or an unmodeled JavaScript transform stops incomplete. This behavior is source-derived and covered by Go pipe/VM tests, but has not yet been compared with a native ClamBC execution on the same program. See [ClamAV's declarations](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.h) and [API source](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c).

These behaviors come from the pinned API implementations and `fmap_readn` in `fmap.h`.

* `test1` returns `0x12345678` exactly when its arguments are `0xf00dbeef, 0xbeeff00d`; every other pair returns `0x55`.
* `read` rejects a negative signed size or absent file mapping with `-1`. A short read succeeds and advances the input cursor by the actual bytes read. Reading at EOF or requesting zero bytes returns zero without moving the cursor. Failure returns `-1` without moving it. The file helper clamps a request to remaining bytes; it does not pad the destination or initialize its unread tail.
* `seek` interprets its signed first argument relative to start/current/end for `whence` 0/1/2. It allows the exact EOF position. Invalid origins and targets outside `[0, file size]` return `-1` and preserve the old cursor. A successful call returns the absolute new offset. Input seeks have no effect on output extraction position.
* `write` appends to an extraction output independent of the input cursor. Negative lengths and write/engine-limit failures return `-1`; otherwise it returns the actual byte count. Upstream lazily creates a private temporary file, including on a zero-length call. The Go adapter uses a bounded memory output and exposes a copy to its caller; it does not use a host filesystem.
* `setvirusname` returns zero and stores the supplied pointer; **the C implementation ignores `len`**. The surrounding scanner interprets the retained name as a detection after successful execution. An integer return value from the program is not itself a verdict. The Go adapter copies an initialized, bounded, NUL-terminated string immediately, preserving names after VM stack frames are retired.
* `file_find` searches from the current input cursor and returns an absolute offset, or `-1` when absent/invalid. It does not change that cursor. The needle length must be in `[1,1024]`. `file_find_limit` additionally requires a positive signed exclusive upper bound. Both use independent **4096-byte windows with no overlap**; a match crossing a window boundary can be missed. The boundary is relative to the starting cursor. The Go implementation deliberately preserves this upstream behavior.
* `file_byteat` takes an absolute unsigned offset and returns a byte in `[0,255]`, or `-1` if it cannot read exactly one byte. It does not move the cursor. Reading at EOF fails.
* Hash sets (APIs 24–29) are per-bytecode-run objects. New returns the next ID; adding an existing key still succeeds, removing a missing key returns `-1`, and contains returns 0 or 1. Done releases a set and reuses the last ID on the next new call. `hashset_empty` returns 1 for an invalid ID; other calls return `-1` for that ID. Upstream forbids use after done, so native execution faults on a reached use of a destroyed non-last slot. Native execution bounds the table to 4,096 sets and 262,144 live keys; hitting either cap is incomplete (`ErrLimit`), not a clean result. The source contracts are in [ClamAV's API implementations](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L564) and [hash-set routines](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/hashtab.c#L741).
* `hex2ui` truncates each argument to one byte, decodes one ASCII hex pair and returns `-1` on an invalid digit. The reference stores the byte in a signed `char`, so values 128–255 sign-extend on the pinned x86_64 profile. `entropy_buffer` counts all 256 byte values and returns Shannon entropy multiplied by `2^26`, truncated to an integer; zero or negative length returns `-1`. Go charges input length to the VM work budget and requires initialized, valid virtual memory. The source is [ClamAV's scalar API implementations](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1213) and [hex conversion helper](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/str.c#L162).
* `fill_buffer` (wire ID 21, `int32_t(uint8_t*,uint32_t,uint32_t,uint32_t,uint32_t)`) moves the unread suffix `[cursor:filled]` to the start of a writable buffer and reads from the current file into the remaining capacity. ClamAV 1.5.4 ignores the last `fill` argument. It checks input EOF before shifting, returns zero on a full buffer because its delegated `read(0)` returns zero, and returns `-1` for invalid lengths/positions. The Go VM bounds the pointer and work, preserves those return/order rules and refuses uninitialized suffix bytes. See [the pinned implementation](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L463) and [declaration](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.h#L3142).
* `debug_print_str` ignores `len`, reads a C string, appends a newline to its debug output, and returns zero. It performs the string-length operation even when debug display is disabled.
* `debug_print_uint` returns zero when debugging is disabled. With upstream debugging enabled its return value comes from `cli_eprintf`; its `%d` presentation is signed decimal despite the unsigned argument type.
* The private `trace_directory`, `trace_scope`, `trace_source`, `trace_op`, `trace_value` and `trace_ptr` APIs (wire IDs 9–14) return zero without dereferencing their text pointer when the scanner's trace level is zero. The [reference VM](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_vm.c#L852-L866) still validates the first pointer against the second argument before dispatch, so the Go adapter does the same. The API implementation is in [ClamAV's source](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L244-L316). Trace-enabled output and callback semantics remain unsupported.
* `debug_print_str_start` returns unsigned `-1` for a null pointer or zero length; otherwise it returns zero. It prints a precision-limited C string with a debug prefix and no explicit newline. `debug_print_str_nonl` also rejects null/zero length, returns zero with debugging disabled, and otherwise returns the count from `fwrite(str, 1, len, stderr)`. In that enabled path embedded NULs do not truncate its bytes.
* `engine_functionality_level` and `engine_dconf_level` take no argument, ignore their context and return `cl_retflevel()` (`CL_FLEVEL`) and `CL_FLEVEL_DCONF`. Release 1.4 defines both as 216 ([`others.h` lines 72–73 at rel/1.4 commit `5853e1396777bae4d909cd3dd44f58352e7cf9b3`](https://github.com/Cisco-Talos/clamav/blob/5853e1396777bae4d909cd3dd44f58352e7cf9b3/libclamav/others.h#L72), SHA-256 `566c9637098e3d2bf93a457aa53a8fc3eaece6e47ad0611f09f17794af9da32a`; implementations at [`bytecode_api.c` lines 1521–1531](https://github.com/Cisco-Talos/clamav/blob/5853e1396777bae4d909cd3dd44f58352e7cf9b3/libclamav/bytecode_api.c#L1521), SHA-256 `9066485598bc711a14f275f555037efa8e5e7f078d119f19c4e6c3ab92cc9109`). The declarations at that commit ([`bytecode_api_decl.c`](https://github.com/Cisco-Talos/clamav/blob/5853e1396777bae4d909cd3dd44f58352e7cf9b3/libclamav/bytecode_api_decl.c#L293), SHA-256 `b0f8ca23e7f55abc00980ffd893ed21d1cfab3f57cbe4cda6bcfcdc84bf54156`) place them at wire IDs 66 and 67 with prototype type 12 (`{32}`: 32-bit result, no argument), the same positions as the pinned revision above. The Go adapter returns the exported `EngineLevel` constant for both. Feed programs use it to choose between code paths written for older and newer engines, so it must equal the level whose rule selection the loader follows; reporting it does not make unsupported APIs, globals or hooks available. The signature loader now selects rules at level 234, matching pinned ClamAV 1.5.4 `CL_FLEVEL` and `CL_FLEVEL_DCONF` ([`others.h` lines 61–70](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/others.h#L61-L70)); the release-1.4 details above remain historical API evidence. The neighbouring IDs 68 and 69 (`engine_scan_options`, `engine_db_options`) return legacy masks of the live scanner options and database load options in [upstream `bytecode_api.c` lines 1533–1717](https://github.com/Cisco-Talos/clamav/blob/5853e1396777bae4d909cd3dd44f58352e7cf9b3/libclamav/bytecode_api.c#L1533). The Go VM accepts an explicit profile and the native scanner supplies its enabled-module masks; a standalone run without that profile fails only if it reaches an option query.
* The pinned [host implementation](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1713-L1773) defines wire APIs 75 (`version_compare`), 76 (`check_platform`) and 90 (`running_on_jit`). `version_compare` compares equal nondigit bytes, then unsigned numeric runs, and returns -1/0/1. Its `unsigned long` accumulators are not reset between numeric fields; Go preserves this, including 32-bit wrap on Windows. The reference's digit loops can read a byte past a declared length; Go checks the bound first. `check_platform` compares the current three environment platform words field by field, accepting an all-ones query field as ANY. It uses the same modeled environment record as API 72, whose Linux/Windows compiler-version fields still need a native oracle. `running_on_jit` returns zero because the Go VM has no JIT. Direct and serialized Go tests plus five harmless unsigned ClamBC fixtures match the pinned native macOS interpreter for JIT, platform wildcard, exact platform, mismatch, and the numeric-accumulator edge case ([v188 oracle](../../../docs/edr/native-engine/audits/2026-10-31-v188-clambc-platform/REPORT.md)). Native Windows/Linux checks and complete platform environment parity remain open.
* [Startup control APIs 73 and 74](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1680-L1712) return `-1` outside kind 1. Inside startup, a false condition returns the current disable status, `disable_jit_if` raises it to one unless already two, and `disable_bytecode_if` raises it to two. The reference applies status two after startup by turning off every ClamBC program, while ordinary signatures remain loaded ([preparation source](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode.c#L2593-L2653)). The Go loader applies that mode to one immutable signature generation and restores it on incremental feed replacement. Six harmless native ClamAV CLI scans agree on callback suppression and ordinary rule retention ([v189 oracle](../../../docs/edr/native-engine/audits/2026-11-01-v189-startup-control/REPORT.md)). A failed Go startup run still rejects the new generation rather than publishing one with bytecode disabled: an unsupported Go operation could have succeeded upstream, so treating it as a reference disable would be an unverified clean decision.
* [Input switching, wire API 71](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1621-L1669), changes the active `fmap` to a snapshot of the output file or restores the original `fmap`. It preserves the bytecode offset and updates the `file_size` context global; file-backed pipes read the current `fmap`. The Go VM models those effects and invalidates pointers borrowed from the extracted mapping after switch-back. A reached `extract_new` while mapped remains incomplete because the upstream routine truncates the same output file ([source](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L502-L537)); mapped reads after truncation are platform-dependent. The [v190 native differential](../../../docs/edr/native-engine/audits/2026-11-01-v190-input-switch/REPORT.md) confirms a switched-output detection and a clean trigger control.
* [Extracted-container typing, wire API 70](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L1614-L1619), stores a requested type up to `CL_TYPE_IGNORED` and passes it to [the child scan](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode_api.c#L502-L537). ClamAV bypasses ordinary file typing when that value is explicit ([scan dispatch](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/scanners.c#L4451-L4467)). The Go callback now preserves this type to the bounded recursive child path. Direct callers with only an untyped callback stop incomplete on a reached nonzero type. The [v191 native differential](../../../docs/edr/native-engine/audits/2026-11-01-v191-container-type/REPORT.md) covers a positive `CL_TYPE_OTHER` target-14 child match, the no-type and invalid-type controls, and a numeric gap that remains conservative/incomplete. `PART_ANY`, `ERROR`, numeric gaps and parser paths not faithfully modeled remain incomplete when reached.

The Go adapter follows a deterministic **debug-disabled return-value profile**, while capturing bounded diagnostic strings for callers. It never writes diagnostics to standard error. Capture holds at most 64 KiB; once a message does not fit, it and every later message are dropped and `Result.DiagnosticsTruncated` is set. Upstream debug output has no effect on execution when disabled, so a full capture never fails or changes a run; operands are still validated and their work is still charged, and `debug_print_str` still walks its whole string. It records signed decimal for `debug_print_uint`, truncates `_start` at the first NUL, and retains the full declared bytes for `_nonl`. Exact terminal-prefix formatting is not a compatibility promise.

`bytecode_rt_error` logs its packed source location (`line = locationid >> 8`, `column = locationid & 255`) and returns zero; despite its name it does not abort upstream execution. The native adapter records the location in bounded diagnostics. Negative source-line values preserve the unsigned decimal presentation used by the C warning.

The arithmetic APIs calculate `ilog2(a,b) = 2^26 * log(a/b) / log(2)`, `ipow(a,b,c) = c * pow(a,b)`, `iexp(a,b,c) = c * exp(a/b)`, `isin(a,b,c) = c * sin(a/b)`, and `icos(a,b,c) = c * cos(a/b)`, using floating-point division. `ilog2` inputs are unsigned; the other inputs are signed. Every calculation uses the source helper's rounding sequence: subtract 0.5 for a negative value or add 0.5 otherwise, then truncate for its integer return. `iexp` returns an unsigned integer; the others return signed integers. A zero denominator returns `0x7fffffff`, and `ipow(0, negative exponent, c)` returns the same sentinel. Native code uses Go's `math` implementation and rejects nonfinite or out-of-range integer conversions with `ErrRuntime`; these casts have undefined behavior in the C source. It tests the truncated value against its target range, so representable extrema and fractional values that truncate to zero remain valid. Exact parity near transcendental rounding boundaries across C math libraries is not established by one fixture.

## Memory, errors, and limits

The upstream [VM pointer resolver](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode_vm.c#L641) validates the pointer argument using the second argument as an unsigned byte length before calling most pointer APIs. Thus a negative `read` size may fault pointer validation before the C implementation returns `-1`. Null pointers are invalid even for zero-length VM calls. Upstream's general pointer resolver also rejects one-past-end zero-length pointers; that peculiarity is distinct from the host API's zero-byte read behavior. The native virtual memory model must not be confused with C addresses.

The Go adapter validates pointer spans and initialization through VM memory. Input reads require a writable destination for the whole declared request, but mark only bytes actually read as initialized. Source bytes consumed by pointer APIs must be initialized. For the two APIs whose C implementation ignores length, it validates the declared span, then reads a NUL-terminated string within virtual memory and the configured cap. This accommodates callers whose `len` excludes their terminating NUL while preventing C's unbounded string access. Uninitialized, read-only destination, retired, null, and out-of-bounds pointers produce `ErrRuntime`. It returns 32-bit `0xffffffff` for ordinary API `-1`, keeping this separate from a VM failure. Native nil input is an empty file snapshot; it is not a missing ClamAV `fmap` object.

Native limits are 16 MiB accumulated extraction output and 256 bytes per copied virus label. Diagnostic capture is limited to 64 KiB but is truncated silently, as described above. Work is charged against the shared execution budget, including file-search windows and copies, and observes context cancellation. Resource exhaustion returns `ErrLimit`; it must never be interpreted as a completed clean scan. The signature compiler separately gates the supported logical-callback profile; the adapter alone does not activate a feed.

Full extraction compatibility additionally needs `extract_new`, recursive scanning of completed output, the final implicit output flush, shared scanner limits, and propagation of child detections. Upstream `extract_new` scans the output then reuses/truncates its temporary file; it is not just a buffer reset. Returning a successful write while ignoring the resulting output at scan integration would omit detection behavior.

## Interpreter semantics the validator follows

These behaviors come from the pinned `bytecode.c` and `bytecode_vm.c`. Where the interpreter's result is defined, native execution reproduces it; where it has no native equivalent, the program is rejected or the affected value faults at run time.

* **Instruction size classes.** `parseBB` sets `interp_op = opcode * 5` and adds a size class only for instruction types up to 65 ([bytecode.c line 1429](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L1429)); any other pointer type keeps the one-bit class. COPY, LOAD, STORE, SELECT, RET, comparisons and GEP1 dispatch on that class (for example `OP_BC_COPY * 5` at [bytecode_vm.c line 1072](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode_vm.c#L1072) copies one bit, and GEP1 takes a stack-relative "untested case" path). The native validator therefore rejects those instruction widths, and function results, unless they are integers or type 65. GEPZ is unaffected because the loader overrides its class ([bytecode.c lines 2347–2349](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L2347)); pointer-typed locals and arguments stay valid because loads, stores and argument copies read their 64-bit values.
* **Direct-call arguments.** The loader maps call operands with `MAPPTR` ([bytecode.c line 2318](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L2318)): a global becomes `0x80000000|offset` and an addressed local `0x40000000|offset`. `OP_BC_CALL_DIRECT` copies arguments with `READOLD8/16/32/64` ([bytecode_vm.c line 1007](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode_vm.c#L1007)), whose `CHECK_GT(func->numBytes, p)` returns `CL_EBYTECODE` for such operands because `CL_BYTECODE_SAFE` is always defined (line 41). Those arguments are rejected natively; constants and plain values are accepted.
* **Global initializers.** `cli_bytecode_prepare_interpreter` skips globals with type IDs below 65 and writes nothing for structs ([bytecode.c lines 2154–2206](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L2154)), so both read as zero. For an array whose element size is 1, 2, 4 or 8 bytes it stores the first `numElements` raw components, truncated to the element size; an array of pointers therefore holds raw offset and ID numbers, and an array of `i1` holds whole bytes. Other element sizes stay zero. A top-level pointer global is composed from its (offset, global) pair. Its (0, 0) spelling, including the compact zero initializer, becomes a pointer to offset zero of the shared global block rather than null; the native per-object memory model cannot represent that, so the global's bytes are left uninitialized and reading them faults.
* **Call frames.** The interpreter allocates frames on a reusable stack and limits only depth and time. Native frames reuse retired region slots with a new generation, bounding live memory rather than the number of calls.

## Logical signatures and hook integration contract

The following describes the broader upstream hook contract. The initial September 23 probe ran only logical callbacks; the current scanner also dispatches PE, PDF, ELF and Mach-O hooks as described in [README.md](README.md). Additional pinned sources are [database registration](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/readdb.c#L2396), [logical evaluation](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/matcher.c#L845), [sub-signature accounting](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/matcher-ac.c#L1803), and the scanner bridge in `bytecode.c`. These were fetched at the pinned commit and their Git blobs checked against its tree. SHA-256: `readdb.c` = `71b291130d3cd93e539d91ef3fbda6f8959b43e582bb2129f3c17c4f4a8891c5`; `matcher.c` = `f5d10d2bf998c7f9391968e1dbf413c09f2ed5e5b9b91806873dfeef66a0c9a1`; `matcher-ac.c` = `e01fc7782d524620c3802cfb6a14e24a592c9a9838fd95d7e200857a80e613d5`.

The [kind enumeration](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode_api.h#L62) assigns generic=0, startup=1, logical=256, PE unpacker=257, PDF=258, PE all=259, preclass=260, ELF unpacker=261, and Mach-O unpacker=262. Database registration requires kind 256 to contain a logical-signature line. It loads that expression with an associated bytecode index. A nonlogical hook with a logical expression instead receives a hook-match identifier: expression matching enables the hook, but execution waits for the corresponding parser phase and its metadata. Only one startup bytecode may be registered. The database loader rejects unhandled kinds, including generic programs; passing generic interpreter fixtures is not sufficient for database activation.

The expression is only one condition. Upstream checks macro matches and target-description conditions including container ancestry, file size, entry point, section count, and icon groups before dispatching bytecode. A handler-type signature can trigger a bounded scan with a different interpretation of the file rather than a malware verdict. At logical dispatch, bytecode function zero receives the current file map, 64 sub-signature counts, and 64 **first** match offsets. Counts start at zero; missing offsets start at `CLI_OFF_NONE = 0xfffffffe`, distinct from `CLI_OFF_ANY = 0xffffffff` ([constant definitions](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/matcher.h#L253)). Ordinary repeated/nonincreasing offsets are not counted again by `lsig_sub_matched`; partial patterns have a different equality check, and macro sub-signatures can alter counts. The first offset is retained independently of the latest one. A native scanner must either supply these semantics or reject affected signatures.

External global IDs from [clambc.h](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/clambc.h#L123) are:

| ID | Host value |
| --- | --- |
| `0x8000` | `__clambc_match_counts`: 64 unsigned 32-bit values |
| `0x8001` | `__clambc_kind`: unsigned 16-bit value |
| `0x8002` | Legacy `GLOBAL_VIRUSNAMES`; no binding in the generated API globals table |
| `0x8003` | `__clambc_pedata`: PE hook metadata structure |
| `0x8004` | `__clambc_filesize`: one unsigned 32-bit value |
| `0x8005` | `__clambc_match_offsets`: 64 unsigned 32-bit values |

They are virtual host objects, not ordinary user-declared globals. The `G` header's maximum external ID does not grant arbitrary addresses. Native bindings for match counts, kind, file size and match offsets are read-only and per execution; PE and legacy name bindings remain unsupported. Count and offset bindings require explicit scanner context. Upstream `context_safe` installs fallback match counts beginning with dummy `0xdeadbeef` values when no counts were supplied; those are harness defaults, not real matches. Do not use them as scanner evidence or infer logical semantics from a plain unit harness.

`cli_bytecode_runlsig` reports a detection only after successful execution retains a virus name. The function's integer return is otherwise informational. Upstream suppresses some execution failures unless the overall scan timed out; the native engine instead needs an incomplete/error result for unsupported or exhausted execution. Hook execution has additional contracts: `0xcea5e` sets its break flag; integer zero can cause unpacked output to be scanned; and names beginning `BC.Heuristics` follow potentially-unwanted classification. Output lifecycle, detection classification, hook ordering, trigger state, and resource propagation must be implemented together before those kinds can be activated. A fallback that executes every hook immediately or treats every nonzero integer as detection is incompatible.

The bytecode header also declares minimum/maximum engine functionality levels; zero means an absent bound. The embedded logical signature has its own Engine constraints, and upstream rejects disagreement that would load the bytecode but skip its logical trigger. The source reads `targetExclude` into metadata, but this bounded source inspection has not established its complete activation semantics. Preserve it and reject unsupported constraints rather than silently treating them as unrestricted.

### Name expansion belongs to the compiler

`VIRUSNAME_PREFIX("Test")` and `VIRUSNAMES("A", "B")` describe the prefix and suffix catalog. `foundVirus("A")` initially calls `setvirusname` with the suffix and length zero ([macro lines 346–359](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/headers/bytecode_local.h#L346)). The logical compiler replaces this with a pointer to the complete constant string `Test.A` and length six, excluding its terminating NUL ([lines 1701–1777](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/libclambcc/ClamBCLogicalCompiler.cpp#L1701)). It requires a constant name and a declared nonempty suffix. An empty suffix is accepted regardless of the declared suffix set and becomes the bare prefix: `foundVirus("")` may report `Test` even when the catalog is `Test.{A,B}`. Prefixes permit alphanumeric characters, `_`, `-`, and `.`; suffixes exclude `.` ([lines 1606–1623](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/libclambcc/ClamBCLogicalCompiler.cpp#L1606)).

The generated `Test.{A,B}` name is informational. The compiler sorts suffixes, omits empty suffix members, and explicitly notes that editing the header does not change names embedded in bytecode ([lines 1652–1692](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/libclambcc/ClamBCLogicalCompiler.cpp#L1652)). Upstream's runtime `parseLSig` merely retains the logical-signature line; its former prefix/suffix parsing is commented out ([bytecode.c lines 688–705](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L688)). `setvirusname` itself stores the supplied full name without validating it against that catalog, and does not prepend anything ([API lines 169–174](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode_api.c#L169)). Therefore the native adapter must not prepend `Test.` to `Test.A`, return the literal braces as the detection name, or assume the header independently authenticates the runtime label.

If native activation chooses to enforce a finite label catalog, that is a stricter native policy, not an upstream runtime rule. For `Test.{A,B}`, it should at least admit `Test`, `Test.A`, and `Test.B`; a label outside the policy must produce an incomplete/error result rather than a clean verdict. Empty-prefix handling needs its own explicit profile: the pinned compiler's concatenation expression would insert a leading dot for a nonempty suffix with an empty prefix, whereas the older pinned `matchwithread.cbc` embeds a complete name without that dot. Do not infer universal normalization across compiler generations from the visible braces.

### Successful execution, return values, and classification

The logical path initializes context, selects function zero, supplies counts/first offsets/current file, and invokes the interpreter ([bytecode.c lines 2840–2870](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L2840)). On successful execution, a retained name is passed directly to `cli_append_virus`; otherwise the integer result is only logged ([lines 2882–2894](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L2882)). Thus success plus a label can detect even with integer zero, while a nonzero integer without a label does not detect. The special hook-break value is not acted on by the logical-only path. Multiple `setvirusname` calls overwrite the stored pointer, so the final retained name wins in this implementation. The native adapter copies the string to avoid pointer-lifetime problems.

Runtime failure is separate: the upstream logical bridge resets the context and ordinarily suppresses the error unless the overall scan has timed out ([lines 2871–2880](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L2871)). The native implementation deliberately propagates cancellation, runtime faults, and budget exhaustion as incomplete/error and discards partial output/labels. This difference must remain explicit; neither a partial label nor its absence establishes a completed scan after failure.

The final label also controls upstream classification. [`others.c` lines 1655–1677](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/others.c#L1655) routes `PUA.`, `Heuristics.`, and `BC.Heuristics.` to potentially-unwanted indicators, `Weak.` to weak indicators, and other labels to strong indicators; heuristic-precedence configuration can promote a potentially-unwanted indicator. False-positive hashes and application callbacks can still suppress the alert. These rules apply to logical bytecode as well as other signatures. Native activation must implement the intended mapping or reject unsupported classification labels explicitly. This path does not append `.UNOFFICIAL`; that suffix is added when allocating ordinary database names in [readdb.c lines 101–125](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/readdb.c#L101), not by the bytecode runtime label path.

### Entrypoint and activation gates

The compiler sorts `entrypoint` first ([Analyzer lines 43–50](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/libclambcc/ClamBCAnalyzer.cpp#L43)) and requires it to exist with zero parameters ([lines 220–226](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/libclambcc/ClamBCAnalyzer.cpp#L220)). The logical runtime calls function zero without supplying any parameters. Its result accessor reads 32 bits ([bytecode.c lines 1966–1969](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L1966)). This inspection did not find a separate analyzer requirement that the entrypoint's declared result be exactly i32. Requiring `i32 entrypoint(void)` for native activation is a clear, conservative supported profile, rather than a claim that all upstream programs are rejected for any other return declaration.

For initial logical-only integration, activation must require kind `BC_LOGICAL=256`, a valid nonempty LDB trigger, supported descriptors/sub-signatures, and the accepted entrypoint prototype. Other kinds, every unsupported API/global/opcode, and invalid declarations fail before replacing the active database, including unused or unreachable unsupported features. The upstream database loader's kind and trigger gates are at [readdb.c lines 2396–2459](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/readdb.c#L2396). Its signature trust gate normally rejects unsigned bytecode unless unsigned loading is enabled ([lines 2355–2362](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/readdb.c#L2355)); native publisher authentication belongs to the signed feed pipeline.

Header minimum/maximum functionality bounds are inclusive; zero disables that individual bound. Upstream rejects an otherwise supported format when the running engine level falls outside either nonzero bound ([bytecode.c lines 610–643](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L610)). LDB `Engine:min-max` is checked separately and inclusively by [readdb.c lines 2054–2064](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/readdb.c#L2054). A native implementation cannot claim a recent ClamAV functionality level merely to pass these checks; it needs a documented compatibility level plus semantic validation. The target belongs to the LDB descriptor and must match the scanned representation. The header's `targetExclude` is a different field: the pinned writer always emits zero and has an override TODO ([Writer lines 219–221](https://github.com/Cisco-Talos/clamav-bytecode-compiler/blob/a1830a442110325d04708145437a5312fc6ab6f9/libclambcc/ClamBCWriter.cpp#L219)). Nonzero values remain explicitly unsupported in the native profile.

### Output-producing bytecode lifecycle

`write` is not a harmless diagnostic sink. Upstream's interpreter and JIT completion paths both call `extract_new(ctx, -1)` for pending extracted output ([bytecode.c lines 1892–1913](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode.c#L1892)). That API updates scan limits, scans the output recursively with its container type, propagates a child virus name, and truncates/recycles the output ([bytecode_api.c lines 534–571](https://github.com/Cisco-Talos/clamav/blob/72cd48c9faed4fa4afc22bc4ed0b9b19f8d3f8f7/libclamav/bytecode_api.c#L534)). The sandbox's bounded `Result.Output` snapshot implements none of that scanner lifecycle by itself.

The engine now supplies a synchronous callback into its ordinary recursive child scanner. API 3 (`write`) buffers up to 16 MiB per output file, API 22 (`extract_new`) scans and resets the previous file, and VM termination scans any pending final output. Child scans share the parent generation, ancestry, deadline, recursion/file/size/aggregate-byte limits. A child detection wins even if later VM instructions fail. A direct matcher/VM run without the callback still returns `ErrExtraction` on reached output operations; resource limits or undecidable child content remain incomplete. API 71 switches to an output snapshot for bytecode reads, subject to the mapped-truncation caveat above. API 70 carries a forced child type through the scanner, with unmodeled values and parser paths incomplete. Other unknown extraction APIs fail their declarations. Partial and multi-window LZMA decompression remains incomplete. The official unpackers' reached-output behavior still needs differential validation on representative benign and labelled corpora; a zero-length output observed on one input is not proof that the same program cannot unpack malware on another input.

The v38 correction also scans pending output after a VM fault. The pinned [ClamAV 1.5.4 interpreter](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode.c#L1809) calls `extract_new(-1)` after execution when the output file is open and the result is not `CL_VIRUS`; it does not require VM success. A harmless write-then-invalid-opcode fixture produces the same child-hash detection in ClamAV and Go, while its benign control stays clean ([differential receipt](../../../docs/edr/native-engine/audits/2026-10-26-pending-output/REPORT.md)).

The v40 API 89 implementation follows the pinned [ClamAV `matchicon` source](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/matcher.c#L689-L742): both string buffers are checked by the VM; lengths above 127 and a missing PE entry point return `-1`. For valid calls, that source zeroes a temporary `cli_exe_info` but does not initialize its `ndatadirs` or `dirs[2]`; [`findres`](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/pe.c#L315-L330) immediately returns when `ndatadirs < 3`. Thus the 1.5.4 API always returns no-match, including where an ordinary LDB icon rule matches. The header calls API 89 PE-hook-only, but [logical callback dispatch](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/libclamav/bytecode.c#L2701-L2734) supplies PE metadata too, and official `3986188.cbc` is logical. The [v40 oracle](../../../docs/edr/native-engine/audits/2026-10-26-matchicon/REPORT.md) covers logical/hook, positive ordinary LDB, absent groups, invalid length and benign controls. A later ClamAV release that repairs this source path requires a separate semantic profile; the Go engine must not silently treat 1.5.4's bug as universal.
