# UTMStack EDR — Signature (CVD) Auto-Update Mechanism — Design & Evaluation

**Status:** Design + recommendation (for review)
**Date:** 2026-07-02
**Scope:** How the EDR keeps ClamAV signature databases current — the default (official CDN) path, and the planned "UTMStack server as mirror" path — plus an evaluation of *which* client mechanism to use for the mirror.

---

## 1. Purpose

The EDR's detection strength is only as good as its signature database. This document specifies how those signatures (ClamAV **CVD** databases) are kept up to date on every endpoint, in two modes:

1. **Default — official ClamAV CDN.** Each endpoint pulls directly from ClamAV's CDN. Works today, standalone.
2. **UTMStack-hosted mirror (planned).** The UTMStack server hosts the CVD update service and every agent pulls from it — one upstream fetch fans out to the fleet.

It then answers the core question: **for the mirror path, do we (A) use ClamAV's native mirror mechanism, or (B) reuse the agent's existing dependency downloader that already pulls artifacts from the UTMStack master server?**

**Bottom line up front:** use **(A) the ClamAV-native mirror** — the UTMStack server runs the official `cvdupdate` tool and serves the CVD directory; agents point **freshclam** at it via `PrivateMirror`. Reuse the UTMStack server's existing HTTP/TLS *hosting* infrastructure, but **do not** reuse the agent's dependency downloader for the *client-side fetch*. Rationale in §4.

---

## 2. Background — how ClamAV signature updates actually work

Understanding this is what drives the recommendation.

- **CVD files.** Signatures ship as `main.cvd`, `daily.cvd`, and `bytecode.cvd` — compressed, **digitally signed** containers. `daily.cvd` changes often (multiple times/day, ~50–60 MB full); `main.cvd` rarely; `bytecode.cvd` occasionally.
- **Incremental `.cdiff` updates.** Rather than re-download a 60 MB database on every change, freshclam fetches small **cdiff** patches (often a few hundred KB) and applies them locally. This is enabled by `ScriptedUpdates yes` and is the single biggest bandwidth lever at fleet scale.
- **Integrity by signature, not by transport.** Every CVD is signed by ClamAV (Talos). `freshclam`/`clamd` **verify that signature on download and on load**, regardless of where the file came from. A mirror — even a self-hosted one — **cannot tamper** with signatures; a modified CVD is rejected. This property is central to why a mirror is safe.
- **`freshclam`** is the official update client: it checks the current version, fetches full CVDs or cdiffs, verifies signatures, retries with backoff, and hands off to clamd (which reloads via `SelfCheck`). We already run it (`edr/feed`).
- **Rate limits are real.** ClamAV's CDN (Cloudflare-fronted) enforces per-source limits and returns HTTP 429 / can **block** sources that poll too aggressively. ClamAV's official guidance: organizations with more than a handful of endpoints **should run a private mirror** using **`cvdupdate`** (the official mirror tool) rather than pointing every endpoint at the CDN. So for a fleet, a mirror is not merely an optimization — it's how you avoid being throttled or blocked.
- **`cvdupdate`.** ClamAV's supported tool for running a private mirror: one host fetches CVDs + cdiffs from the CDN (respecting rate limits, on a cron), and lays them out in a directory served by any web server. Endpoints' freshclam then use that URL via `DatabaseMirror`/`PrivateMirror`.

## 3. Update modes

### 3.1 Default — official ClamAV CDN (implemented)

`freshclam.conf` (auto-generated by `edr/engine`) uses:
```
DatabaseMirror database.clamav.net
ScriptedUpdates yes
Checks 24            # ~hourly; CDN rate-limits, do not over-poll
```
Each endpoint pulls directly. Zero server-side work; requires outbound internet from every endpoint; **does not scale past a modest fleet** without risking CDN throttling.

### 3.2 UTMStack server as mirror (planned)

The UTMStack server hosts the CVD update service; every agent pulls signatures from it. Goals: **one upstream fetch fans out to the fleet, no CDN rate-limit exposure, works on restricted/air-gapped networks, and central control of signature rollout.**

The EDR already has the **client-side hook** for this: setting `signature_mirror` in `edr.json` switches the generated `freshclam.conf` from `DatabaseMirror database.clamav.net` to `PrivateMirror <url>`. The remaining work is **server-side** (§5.1) — an external dependency on the platform team.

## 4. Evaluation — which client mechanism for the mirror?

Two ways an agent could pull CVDs from the UTMStack server.

### 4.1 Option A — ClamAV-native mirror (freshclam `PrivateMirror`) — **RECOMMENDED**

The UTMStack server runs `cvdupdate` and serves the resulting CVD directory over HTTP(S) (reusing the server's existing web/TLS stack). Agents keep using **freshclam**, pointed at that URL via `PrivateMirror`.

**Pros**
- **Keeps cdiff incrementals.** Agents pull tiny patches, not full 60 MB databases — the decisive bandwidth win at fleet scale.
- **Keeps ClamAV's integrity model.** CVDs stay ClamAV-signed; freshclam verifies signatures on download. The mirror is untrusted-by-design and can't tamper.
- **Uses the officially supported pattern.** `cvdupdate` exists for exactly this; freshclam's retry/verify/version logic is battle-tested. We write ~zero new update code — just a config value we already support.
- **Version-aware.** freshclam only fetches when a newer version exists, and only the delta.
- **Air-gap friendly.** Server syncs from the CDN (or is seeded manually); endpoints never touch the internet.
- **Reuses UTMStack hosting infra.** The mirror is just a directory served by the same web server / behind the same TLS the platform already runs — same host, same certs, a different path.

**Cons**
- Server must run `cvdupdate` on a cron and serve a directory (modest, well-documented server-side work).
- freshclam's `PrivateMirror`, once set, does **not** auto-fall-back to the CDN if the mirror is down — fallback must be designed (§5.4).

### 4.2 Option B — reuse the agent's built-in dependency downloader

The agent's `dependency` mechanism (`dependency.Reconcile` → `shared/http.DownloadFile` from `https://<server>:9001/private/dependencies/agent/<file>`, version-tracked in `dependencies.json`, whole-file download + optional unzip) already ships binaries (updater, EDR) from the master server. Option B would ship the CVDs the same way: download `main.cvd`/`daily.cvd`/`bytecode.cvd` as "dependencies" into the engine database directory, bypassing freshclam for updates.

**Pros**
- One transport/auth/TLS channel to the server (the one the agent already uses); nothing new to open in the firewall.
- No freshclam mirror configuration; the agent controls fetching.

**Cons (decisive)**
- **Loses cdiff incrementals.** The dependency mechanism ships **whole files by version**. `daily.cvd` would be re-downloaded in full (~60 MB) every time it changes — several times a day, times every endpoint. That is precisely the bandwidth explosion cdiffs exist to prevent; it's *worse* per-endpoint than the CDN default.
- **Reinvents version tracking.** freshclam already tracks CVD versions and deltas; Option B forces us to detect new ClamAV DB versions and bump a manual dependency `Version` string to trigger re-download — custom, fragile logic duplicating freshclam.
- **Bypasses freshclam's proven update path** (retry/backoff, partial-download handling, signature verification-on-fetch), replacing it with our own — more code, more failure modes.
- **Does not save the server-side work.** The server *still* has to obtain the CVDs from ClamAV somehow (i.e. still run `cvdupdate` or equivalent). So Option B keeps the server cost of Option A while throwing away cdiffs and freshclam's smarts on the client.
- **Awkward split of responsibility.** clamd expects freshclam-managed databases (SelfCheck/reload). Dropping files underneath it works, but you now have two systems (dependency downloader for updates, clamd for loading) that don't know about each other.

### 4.3 Comparison

| Dimension | A: ClamAV-native mirror (freshclam) | B: Agent dependency downloader |
|---|---|---|
| Incremental (cdiff) updates | ✅ yes — KB-scale | ❌ no — full CVD each change (~60 MB) |
| Signature integrity | ✅ freshclam verifies | ✅ clamd verifies on load (but custom fetch) |
| New client code | ✅ none (config only, already built) | ❌ custom fetch + version tracking |
| Version awareness | ✅ native | ❌ manual/custom |
| Server-side work | `cvdupdate` + serve dir | `cvdupdate` (or equiv) + serve via deps endpoint |
| Reuses agent channel | ⚠️ separate URL (same host OK) | ✅ existing channel |
| Fleet bandwidth | ✅ minimal | ❌ high |
| Air-gap capable | ✅ | ✅ |
| Official/supported pattern | ✅ this is *the* pattern | ❌ bespoke |

### 4.4 Recommendation

**Adopt Option A.** The only thing Option B buys is a single transport channel — and it pays for that with a large fleet-bandwidth regression, reinvented version/verification logic, and *the same* server-side cost. Option A reuses what matters (the UTMStack server's hosting/TLS and the ClamAV-native, cdiff-capable, signature-verified update path) and requires essentially no new client code, because the `signature_mirror → PrivateMirror` hook already exists.

Reuse the agent's dependency mechanism for **binaries** (the EDR executable, the engine build) — that's what it's good at. Use **freshclam against a `cvdupdate` mirror** for **signatures** — that's what freshclam is good at. Right tool for each artifact type.

## 5. Recommended architecture (Option A) in detail

```
   ClamAV CDN (database.clamav.net)
            │  cvdupdate (cron, rate-limit-compliant)
            ▼
   ┌───────────────────────────────────────────┐
   │ UTMStack server                            │
   │  • cvdupdate → /var/lib/clamav-mirror/     │
   │  • web server serves it at                 │
   │    https://<server>/clamav/  (existing TLS)│
   └───────────────┬───────────────────────────┘
                   │  freshclam PrivateMirror (cdiff, signed, verified)
     ┌─────────────┼─────────────┬─────────────┐
     ▼             ▼             ▼             ▼
  agent+EDR     agent+EDR     agent+EDR     agent+EDR   (whole fleet)
```

### 5.1 Server side (external dependency — platform team)
- Run **`cvdupdate`** on a schedule (e.g. hourly) to fetch `main`/`daily`/`bytecode` CVDs **and their cdiffs** from the CDN into a mirror directory. `cvdupdate` is rate-limit-aware — this single job is the fleet's only CDN contact.
- Serve that directory over the platform's **existing HTTPS** at a stable path (e.g. `https://<server>/clamav/`). No new service needed — a static file route on the current web tier.
- Keep the mirror fresh; monitor `cvdupdate` success (a stale mirror means stale detection fleet-wide — this is now a central point to watch, which is a feature: one place to verify signature currency).

### 5.2 Client side (already implemented in the EDR)
- `edr.json` field **`signature_mirror`**. When set, `edr/engine` writes:
  ```
  PrivateMirror https://<server>/clamav
  ScriptedUpdates yes
  Checks 24
  ```
  When empty (default), it writes `DatabaseMirror database.clamav.net`.
- `edr/feed` runs `freshclam --config-file freshclam.conf` on the configured cadence; on a new signature version it marks clean cache entries stale for lazy re-scan (already built).
- The agent can push `signature_mirror` centrally (it's part of `edr.json`, which the agent controls), so flipping the whole fleet to the mirror is a config push — no re-deploy.

### 5.3 Integrity / security
- CVDs remain **ClamAV-signed**; freshclam verifies on download, clamd on load. A compromised or misconfigured mirror **cannot inject malicious signatures** — verification fails and the update is rejected. The mirror is explicitly untrusted.
- Serve the mirror over **HTTPS** (existing platform TLS) so the transport is also authenticated/encrypted, but signature verification is the real guarantee.

### 5.4 Fallback behavior (design decision — see §9)
`freshclam` with `PrivateMirror` set does **not** automatically fall back to the official CDN if the mirror is unreachable. Options, in order of preference:
1. **Config both, mirror-first (recommended where endpoints have internet):** the EDR writes `PrivateMirror <server>` *and* leaves the CDN reachable via a secondary; freshclam tries the private mirror first. (freshclam supports multiple `PrivateMirror` entries; a CDN fallback needs care because `PrivateMirror` suppresses official mirrors — so a true CDN fallback may require the EDR to detect repeated mirror failures and temporarily regenerate `freshclam.conf` with `DatabaseMirror`.)
2. **Mirror-only (recommended for air-gapped/locked-down fleets):** no fallback by design; a down mirror means stale (not broken) detection until it recovers, and the central mirror is monitored.
3. **EDR-managed failover:** on N consecutive freshclam failures against the mirror, the EDR rewrites `freshclam.conf` to the CDN for one cycle, then retries the mirror. Most robust, small amount of code.

Recommendation: make it a policy field (`signature_fallback: "none" | "cdn"`) defaulting to `none` in air-gapped deployments and `cdn` where endpoints have internet.

## 6. Configuration reference

`edr.json`:
```jsonc
{
  // "" (default) → pull from official ClamAV CDN (database.clamav.net)
  // set → freshclam PrivateMirror at the UTMStack-hosted cvdupdate mirror
  "signature_mirror": "https://utmstack.example.com/clamav",
  "signature_fallback": "cdn",   // planned: "none" | "cdn"
  "sig_update_hours": 4           // freshclam run cadence (feed scheduler)
}
```

Generated `freshclam.conf` (mirror mode):
```
DatabaseDirectory <install>/engine/database
PrivateMirror https://utmstack.example.com/clamav
ScriptedUpdates yes
Checks 24
CompressLocalDatabase no
```

## 7. Rollout phases

1. **Phase 1 (now):** default CDN mode. Ships and works standalone; fine for small deployments and pilots. `signature_mirror` hook present but unset.
2. **Phase 2 (mirror — external dependency):** platform team stands up `cvdupdate` + serves `/clamav/`. Set `signature_mirror` on managed fleets; validate cdiff updates and freshclam verification against the mirror.
3. **Phase 3 (hardening):** implement `signature_fallback` policy + central monitoring of mirror freshness; document the air-gapped deployment path.

---

## 8. External dependencies (platform team)
1. **`cvdupdate` mirror service** on the UTMStack server (cron + static hosting at a stable HTTPS path). This is the one net-new server-side component; it is the same tool ClamAV recommends and is required for both Option A and (implicitly) Option B, so it is unavoidable if UTMStack is to be a mirror at all.
2. Monitoring/alerting on mirror freshness (stale mirror ⇒ fleet-wide stale detection).

---

## 9. Open decisions
- **Fallback policy** (§5.4): default to `cdn` fallback (internet-connected fleets) or `none` (air-gapped)? Recommend per-deployment, default `cdn`.
- **Auto-derive the mirror URL from `cfg.Server`?** Once the platform commits to a fixed mirror path, the EDR could default `signature_mirror` to `https://<cfg.Server>/clamav` automatically when the server advertises mirror capability (e.g. a capability flag from the agent registration), instead of requiring an explicit config. Recommended once the server side exists.
- **Third-party feeds** (Sanesecurity/SecuriteInfo/URLhaus — the biggest real-world catch-rate lever, §9 of the tuning guide): these are also best mirrored centrally (`cvdupdate` supports custom databases). Fold into the same mirror once the base mirror is proven.

---

## 10. Summary

Keep the **default = official CDN** (works today, standalone). For scale, **make UTMStack a mirror using the ClamAV-native path**: the server runs `cvdupdate` and serves the CVD directory over its existing HTTPS; agents use **freshclam `PrivateMirror`** (the client hook is already built via `signature_mirror`). This preserves cdiff incrementals and ClamAV's signature-verified integrity while reusing UTMStack's hosting infrastructure. **Do not** repurpose the agent's dependency downloader for signatures — it would discard incrementals, reinvent version tracking, bypass freshclam's proven pipeline, and still require the same server-side mirror. Reserve the dependency downloader for **binaries**, and let **freshclam** own **signatures**.
